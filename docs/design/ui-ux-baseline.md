# 前端 UI/UX 设计基线

## 1. 文档定位

本文档记录 AI 智能平台 Web 前端的界面结构、交互、响应式和可访问性基线。它适用于个人空间和企业空间，并与菜单权限、页面资源、接口资源和 `permission_code` 设计保持一致。

本文最初用于约束阶段 0 本地运行中心，现已扩展为阶段 1 正式业务工作台的完成态基线。当前正式界面已经覆盖总览、成员、组织、知识生产、知识问答、工作流、运行状态和模型治理；后续页面必须复用同一应用壳层、语义 Token、UnoCSS、Ant Design Theme、焦点管理和权限边界。

| 检查项 | 实际结果 | 结论 |
| --- | --- | --- |
| 桌面视口 `1440×900` | 内容层级清楚，无横向溢出，控制台无警告 | 通过 |
| 移动视口 `390×844` | 无横向溢出，六项服务可读 | 通过 |
| 小屏视口 `375×812` | 无横向溢出 | 通过 |

## 3. 产品界面定位

平台属于高频使用的 AI 生产力和企业治理工具，界面应优先满足扫描、比较、配置和重复操作：

- 内容优先、信息密度适中，避免营销型 Hero、装饰性大卡片和无业务含义的渐变。
- 页面区块使用无框布局；卡片只用于重复条目、弹窗和确实需要被框定的工具。
- 每个页面只设置一个主要动作，其余操作使用次级按钮或更多菜单。
- 使用 `lucide-react` 等统一 SVG 图标，不使用 Emoji 作为结构性图标。
- 所有状态同时使用文字、图标或形状表达，不能只依赖颜色。

## 4. 正式应用壳层

阶段 1 开始建设个人和企业空间的正式页面壳层：

```text
应用壳层
├ 顶部栏
│  ├ 当前空间切换
│  ├ 全局搜索
│  ├ 通知与待办
│  └ 用户菜单
├ 左侧动态菜单
│  ├ 工作台
│  ├ 知识库
│  ├ Agent
│  ├ 工作流与审批
│  └ 系统管理
└ 主内容区
   ├ 面包屑
   ├ 页面标题与操作区
   └ 页面业务内容
```

### 4.1 菜单与路由

- 菜单树来自后端发布的 `MenuRelease` 快照，个人空间和企业空间都执行菜单权限控制。
- React Router 使用 `NavLink` 计算当前激活项，不在组件中写死激活状态。
- 菜单可以调整已注册页面的目录、顺序、名称、图标和可见范围，但不能配置任意组件、任意路由或任意接口地址。
- `MenuApiBinding` 将页面与允许调用的接口统一绑定；前端菜单隐藏只负责体验，后端仍必须执行功能权限、数据权限和字段级 ABAC。
- 菜单项在折叠侧栏中必须保留 Tooltip 和 `aria-label`，不能只留下无法识别的图标。
- 三层及以上页面层级使用面包屑；返回操作必须保持路由、滚动位置、筛选条件和草稿状态。

### 4.2 响应式导航

| 视口 | 导航方案 | 约束 |
| --- | --- | --- |
| `≥1024px` | 固定侧栏 + 顶部栏 | 侧栏可折叠，核心菜单始终可达 |
| `721–1023px` | 窄侧栏或可展开侧栏 + 顶部栏 | 保留当前页面标题和主要操作 |
| `≤720px` | 顶部栏 + 抽屉式菜单 | 不隐藏主导航，不使用复杂多级底部导航 |
| 横屏移动端 | 顶部栏 + 可收起抽屉 | 保留安全边距，避免遮挡内容 |

移动端抽屉打开后应有明确关闭入口、键盘/辅助技术焦点管理和足够的遮罩；不让抽屉成为用户唯一的返回路径。

## 5. 布局与视觉规则

### 5.1 间距和尺寸

- 使用 4/8px 间距节奏，常用层级为 `8 / 16 / 24 / 32 / 48`。
- 桌面主内容设置稳定的最大宽度，长文本每行控制在约 60～75 个字符。
- 移动端正文不小于 `16px`；交互目标不小于 `44×44px`，相邻目标至少间隔 `8px`。
- 固定头部、抽屉、底部操作条必须为滚动内容预留安全区域。
- 使用 `min-height: 100dvh` 等动态视口单位，避免移动浏览器地址栏导致布局跳动。

### 5.2 字体和颜色

- 最终主品牌色使用森林绿 `#176b52`，导航背景使用深绿 `#12332b`，保持平台可信、克制和工作导向的视觉定位。
- 原荧光绿强调色已替换为克制蓝绿色 `#85b7c5`，避免大面积同色系和过强视觉刺激；辅助文字统一为 `#596a63`。
- 业务代码只能引用语义 Token 和 Ant Design Theme，不能在各页面散落重复的十六进制颜色；新增颜色必须先完成用途、对比度和多状态评审。
- 正式业务页面优先使用系统无衬线字体，提高表格、权限、审批和配置场景的扫描效率；宋体只用于品牌或少量内容型页面。
- 正文和重要辅助文字达到 WCAG AA 对比度：普通文字至少 `4.5:1`，大字至少 `3:1`。
- 成功、降级、错误和信息状态需要同时使用文字和图标；红绿不能作为唯一状态区别。

### 5.3 阴影、边框和卡片

- 页面区块默认使用平面分组和细边界，避免“卡片套卡片”。
- 统一使用少量层级阴影：普通内容无阴影，浮层和弹窗使用明确的高层级阴影。
- 卡片圆角保持 `≤8px`，除非组件库规范要求更大。
- 交互状态通过背景、边框、图标或文字权重变化表达，不能通过改变尺寸导致布局抖动。

### 5.4 样式实现边界

项目按 [`ADR-003`](../decisions/ADR-003-adopt-unocss-style-system.md) 使用 UnoCSS 作为新增和迁移页面的主样式路径，但 UnoCSS 不取代设计 Token、Ant Design Theme 和全局可访问性规则。

- 页面布局、间距、尺寸、排版、语义颜色、边框和普通响应式优先使用 UnoCSS。
- 颜色、间距、圆角、层级和动效必须引用项目语义 Token，不在 JSX 中散落重复十六进制颜色。
- Ant Design 组件外观优先通过 `ConfigProvider` Token 调整，不用高优先级 Utility 覆盖内部实现。
- Reset、触控目标、焦点环、减少动效和少量全局 Ant Design 修正继续由全局 CSS 管理。
- 复杂父子状态、复合宽高媒体查询和难以清晰表达的交互可以保留受控 CSS；不以“零 CSS 文件”为目标。
- 条件样式必须使用完整类名映射，确保生产构建可以静态发现；不能运行时拼接 Utility 名称。
- 高频视觉组合可以使用有限 Shortcut，但 Shortcut 不能隐藏页面结构或形成新的不透明组件样式层。

## 6. 状态、反馈和可访问性

### 6.1 加载、空、错误和成功

- 服务列表、表格和页面主体使用固定尺寸 Skeleton，避免异步数据导致 CLS 和首屏跳动。
- 空状态必须说明“当前没有什么”和“下一步可以做什么”，并提供一个明确操作。
- 错误信息靠近出错区域，说明原因、影响和恢复操作；网络超时必须提供重试。
- 异步按钮在请求期间禁用并显示加载状态；成功或失败使用可读的 Toast/Inline 状态反馈。
- 健康检查 `503` 仍应解析响应体，区分“API 不可达”和“依赖服务降级”。
- 状态容器使用 `aria-live="polite"`；加载期间设置 `aria-busy="true"`，完成后恢复为 `false`。

### 6.2 键盘和屏幕阅读器

- 所有可操作元素必须有可见的 `:focus-visible` 焦点环，不能因去除鼠标点击高亮而移除键盘反馈。
- 页面标题按 `h1 → h2 → h3` 顺序组织；路由变化后焦点移动到主内容区域。
- 图标按钮必须提供 `aria-label`；有文字的按钮不重复读出无意义的图标名称。
- 表单使用可见标签、字段级错误和必要的 `aria-describedby`；提交错误后聚焦第一个无效字段。
- 动画遵守 `prefers-reduced-motion`；动画只表达状态变化，不做纯装饰。

## 8. UI/UX 验收门禁

阶段 1 每个页面验收至少覆盖：

1. `375×812`、`390×844`、`768×1024`、`1024×768`、`1440×900` 和一个横屏视口。
2. 无横向滚动；长文本、按钮和表格内容不溢出或遮挡。
3. 触控目标至少 `44×44px`，键盘可以完成主要流程。
4. 正常、加载、空、错误、无权限和降级状态均有明确反馈。
5. 主要文字达到 WCAG AA 对比度；颜色不是唯一状态提示。
6. 菜单、页面、按钮和接口权限来自统一资源/权限编码；直接访问 URL 不能绕过后端校验。
7. 浏览器控制台无未处理异常；关键页面支持深链接和返回状态保持。
8. 开启 `prefers-reduced-motion` 后，页面仍可完整使用。
9. 生产构建与开发环境样式一致，条件类名、响应式类名和 Safelist 没有缺失。

## 10. 变更规则

- 阶段 1 完成后的新页面必须直接复用正式壳层、语义 Token、UnoCSS 和既有焦点行为，不重新引入阶段 0 临时样式。
- UnoCSS 迁移已按 `P1S-01`～`P1S-05` 完成；新增 CSS Module、运行时拼接 Utility 和未登记 Token 由样式门禁拒绝。
- 主色调和字体已经在 `P1G-04` 固定；暗色模式仍需单独立项和完整状态验收，不能只做颜色反转。
- UI/UX 评审结论、设计 Token 或导航结构发生变化时，必须更新本文档并按项目节点规则进行验收和 Git 提交。
