# 后端代码规范

## 1. 目的与适用范围

本文档规定 `apps/api`、`apps/worker` 及后续 Python 后端模块的代码结构、模块接口、数据访问、事务、权限、异步任务、SSE、测试和质量门禁。规范以当前 AI 智能平台架构为事实基础，不照搬普通 CRUD 项目的分层模板。

本规范从合入仓库后立即生效。开发者、自动化工具和代码生成器对后端代码的新增和修改都必须遵守；历史代码在对应业务节点中渐进调整，不为形式统一单独制造大范围重构。

规则优先级如下：

1. 当前需求和已经确认的产品、架构决策。
2. 本文档的后端代码规范。
3. 仓库 `contracts/` 下的 OpenAPI、SSE、事件、策略、错误码和领域契约。
4. [`ai-intelligent-platform-v2-design.md`](../../ai-intelligent-platform-v2-design.md) 的架构与数据写入权定义。
5. 目标模块现有且未被本规范否定的代码模式。

## 2. 技术基线

| 领域 | 当前或已确认基线 | 约束 |
| --- | --- | --- |
| 运行时 | Python 3.12、uv | 以根目录 `pyproject.toml` 和 `uv.lock` 为准 |
| HTTP | FastAPI、Pydantic 2 | REST/JSON 管理与业务接口，OpenAPI 3.1 |
| 数据 | PostgreSQL 16、SQLAlchemy 2 | 工作空间数据强制隔离，ORM 不作为跨模块契约 |
| Migration | Alembic | 共享数据库只有一条 Schema 演进流水线 |
| 异步任务 | Celery、Valkey | PostgreSQL 保存事实状态，任务按至少一次投递设计 |
| 流式输出 | SSE | PostgreSQL 保存恢复事实，支持 `Last-Event-ID` |
| 对象与解析 | MinIO、Tika、独立 Ingestion Worker | 大文件和解析任务不得占用 API 请求进程 |
| 类型与质量 | mypy strict、Ruff | 禁止通过降低全局严格度绕过错误 |
| 测试 | pytest、契约测试、集成测试 | 权限、事务、恢复和 Migration 不得只靠单元测试 |
| 可观测性 | 结构化日志、W3C Trace、OpenTelemetry、Prometheus | Trace 贯穿 HTTP、任务、事件、检索和模型调用 |

尚未安装的 SQLAlchemy、Alembic、Celery、OpenTelemetry 等依赖在对应实施节点引入。本规范不要求为了建立规则提前创建空模块、空 Adapter 或空 Go 工程。

## 3. 模块设计原则

后端优先建设深模块：以较小、稳定的接口隐藏复杂业务规则、权限、事务和外部协议差异。模块接口不仅包含类型签名，还包括调用前置条件、事务语义、错误模式、幂等约束和性能特征。

必须遵守：

- 按业务领域划分模块，不按技术类型建立全局 `services/`、`repositories/`、`models/` 杂物目录。
- 一个业务聚合只有一个写入责任模块；其他模块通过公开接口或版本化事件协作。
- 依赖由应用装配层注入，业务代码不在函数内部创建数据库、模型供应商或外部 HTTP Client。
- 只有行为确实会变化、存在两个 Adapter，或测试需要稳定替换点时才建立接口。
- 接口应接受领域语义明确的参数并返回结果，避免让调用方了解 ORM、框架上下文或内部处理步骤。
- 删除一个模块后，如果复杂性原样散落到多个调用方，说明该模块具有价值；只转发参数且没有隐藏复杂性的浅层封装应删除。

不要求健康检查、简单转换函数和稳定的单表只读查询机械套用完整领域分层。是否拆分以业务规则、安全风险、变化频率和测试价值为依据。

## 4. 目标目录结构

阶段 1 的目标结构如下，目录只在出现真实职责时创建：

```text
apps/api/src/ai_platform_api/
├── app/                              # 应用创建、Middleware、异常映射和依赖装配
├── common/                           # 少量跨领域稳定基础能力
└── modules/
    └── {domain}/
        ├── api/                      # Router、请求/响应 Schema
        ├── application/              # 用例、Command、Query 和事务编排
        ├── domain/                   # 领域规则、状态转换和模块接口
        └── infrastructure/           # SQLAlchemy 与外部系统 Adapter

apps/worker/src/ai_platform_worker/
├── app/                              # Worker 创建、任务注册和依赖装配
├── consumers/                        # 版本化集成事件消费者
└── modules/
    └── {domain}/                     # 与 API 使用相同领域语言的任务处理模块
```

首批领域预计包括 `workspace`、`identity`、`authorization`、`menu`、`knowledge`、`workflow`、`conversation`、`streaming` 和 `model_gateway`。该列表不是要求提前创建空目录。

目录职责：

- `api/` 只负责协议解析、输入校验、调用用例和响应映射。
- `application/` 负责一个业务用例的授权、事务和跨内部实现编排。
- `domain/` 保存不依赖 FastAPI、Celery 和具体数据库的核心业务规则。
- `infrastructure/` 实现数据库、对象存储、模型供应商和外部 HTTP 等 Adapter。
- `common/` 只接收已经证明跨多个领域稳定复用的能力，不作为临时代码存放处。
- API 与 Worker 可以复用领域规则和语言无关契约，但不得通过导入另一个进程的启动模块来共享行为。
- API 与 Worker 出现真实共享实现后，应提取为职责明确的 Python 共享包；不得让 Worker 直接依赖 API Router、应用创建或进程配置，也不得为了假设复用提前建立空共享包。

当前 `main.py`、`routes/health.py`、`schemas.py` 和 Worker 健康模块是阶段 0 过渡结构。正式应用壳层建设时随业务节点迁移，不单独进行无价值重排。

## 5. 模块依赖方向

依赖方向固定为：

```text
api -> application -> domain
infrastructure -> domain
app -> api + application + infrastructure
```

- `domain/` 不得导入 FastAPI、Celery、SQLAlchemy ORM、Valkey Client 或供应商 SDK。
- `application/` 可以依赖领域接口和事务接口，不依赖具体 Adapter。
- `api/` 不直接访问 ORM、Valkey、对象存储或模型供应商。
- `infrastructure/` 可以依赖框架和 SDK，但不能反向决定领域规则。
- `app/` 是依赖装配入口；具体 Adapter 的选择和生命周期在这里集中管理。
- 跨业务模块不得导入对方的 `infrastructure/` 或私有实现。

确有跨模块同步调用需要时，只依赖对方公开的应用接口或查询接口。跨进程、未来跨语言和需要可靠传播的协作使用版本化 HTTP 契约或集成事件。

## 6. 命名与文件职责

### 6.1 命名

- 包、模块、函数和变量使用 `snake_case`，类和类型使用 `PascalCase`，常量使用 `UPPER_SNAKE_CASE`。
- 用例名称使用明确动词和领域对象，例如 `CreateWorkspace`、`PublishMenuRelease`。
- 查询与命令输入分别使用 `XxxQuery`、`XxxCommand`；返回值使用具体领域语义，不使用 `Data`、`Info`、`Manager` 等宽泛名称。
- Pydantic HTTP 模型使用 `XxxRequest`、`XxxResponse`；领域值对象不带 HTTP 技术后缀。
- Repository 按聚合命名，例如 `WorkspaceRepository`，不得建立包含所有表操作的通用 Repository。
- 外部实现以职责命名，例如 `OpenAICompatibleModelAdapter`、`MinioObjectStoreAdapter`。
- 异步任务名称必须稳定且带业务域，例如 `knowledge.parse_document.v1`，不得使用 Python 模块路径作为对外任务协议。

### 6.2 文件职责与规模预算

| 文件类型 | 推荐范围 | 预警范围 | 处理要求 |
| --- | ---: | ---: | --- |
| Router | `≤200` 行 | `201–350` 行 | 按稳定资源或用例拆分 |
| Application 用例 | `≤250` 行 | `251–400` 行 | 拆查询、命令或独立业务能力 |
| 领域模块 | `≤300` 行 | `301–500` 行 | 按聚合规则或状态机拆分 |
| Repository / Adapter | `≤350` 行 | `351–600` 行 | 按聚合或外部能力拆分 |
| 测试文件 | `≤500` 行 | `501–800` 行 | 按行为场景拆分并共享 Fixture |

行数只是职责膨胀预警，不作为机械拆文件的唯一依据。Schema、稳定字典、生成契约和 Migration 不按普通业务文件衡量。

## 7. Python 与类型规范

- 所有生产函数和公开测试辅助函数必须具有完整参数及返回类型。
- 保持 mypy strict；禁止使用无范围的 `# type: ignore`、关闭全局检查或将内部类型退化为 `Any`。
- 外部未知数据使用 `object`、明确 Protocol 或 Pydantic/Schema 校验后再进入业务逻辑。
- 优先使用 `X | None`、`list[X]` 和 `dict[K, V]` 等 Python 3.12 写法。
- 有限状态优先使用 `Literal`、`StrEnum` 或受契约约束的值对象，不使用无语义整数。
- 可变参数不得使用列表、字典或对象实例作为默认值。
- 时间必须是带时区的 UTC `datetime`；禁止在业务代码中使用无时区 `datetime.now()`。
- 外部资源 ID 使用 UUID；数据库内部键不得泄漏为跨模块契约。
- 金额使用整数最小货币单位与 ISO 4217 币种，禁止浮点数。
- 使用 `dataclass(frozen=True)` 或明确不可变模型表达值对象，避免调用方意外修改共享状态。
- 不用异常表达正常业务分支；需要调用方处理的结果应使用明确返回类型或稳定领域错误。

## 8. 模型边界与数据转换

平台区分以下模型，不允许一个模型贯穿全部层级：

| 模型 | 用途 | 禁止事项 |
| --- | --- | --- |
| HTTP Request/Response | 外部协议与 OpenAPI | 不承载 ORM Session 或内部凭证 |
| Application Command/Query | 用例输入 | 不依赖 FastAPI Request 或 `Depends` |
| 领域实体/值对象 | 业务规则与状态 | 不导入 SQLAlchemy ORM 和供应商 SDK |
| ORM Model | 数据持久化 | 不直接返回给 Router、事件或 Worker |
| Event/SSE Model | 版本化跨进程协议 | 不包含 Python 类路径和不可序列化对象 |

- Pydantic `extra` 策略必须明确；安全敏感的输入和内部契约默认拒绝未知字段。
- 转换在职责最近的边缘完成：HTTP 转换位于 `api/`，数据库映射位于 `infrastructure/`。
- ORM 延迟加载不得逃逸出 Repository/事务生命周期。
- 序列化必须明确区分字段缺失、`null`、空字符串和空集合。
- 契约枚举新增值时调用方必须有可观测的兼容策略，不得因未知值静默授予权限。

## 9. FastAPI 接入规范

- 使用 `create_app()` 工厂集中注册 Router、Middleware、异常处理和生命周期资源。
- Router 必须声明稳定前缀、Tag、`operation_id`、请求模型、响应模型和已知错误响应。
- Router 只做协议适配，不写业务规则、不直接访问数据库、不自行提交事务。
- FastAPI `Depends` 只用于接入层和装配层，不进入 Application 或 Domain 函数签名。
- 身份、工作空间、Trace、幂等键和请求 ID 在统一依赖或 Middleware 中解析。
- 不从请求正文或查询参数信任 `actor_id`、角色、字段掩码和策略结果。
- 正常响应和错误响应都必须匹配仓库契约；禁止返回临时字典绕开模型校验。
- 列表接口优先使用游标分页；只有稳定、小规模管理列表使用页码分页。
- 上传、下载、SSE 与普通 JSON 使用独立的内容类型、超时、大小和取消策略。
- Liveness 只判断进程是否存活；Readiness 判断当前是否可承接请求，不在健康检查中执行昂贵业务查询。

## 10. RequestContext 与身份可信链

每个受保护用例接收不可变的 `RequestContext`，至少包含：

```text
request_id
trace_id / traceparent
actor_id
user_id（存在人类账号时）
workspace_id
authentication_method
```

- `RequestContext` 由服务端认证链构建，客户端不能声明可信主体。
- 浏览器 Session、Open API Key、系统任务和内部服务主体采用不同认证 Adapter，但映射到统一上下文。
- 工作空间切换必须重新验证成员关系和状态，不沿用上一空间的权限决策。
- Worker 从签名或可信任务元数据恢复最小上下文；不得信任普通事件载荷伪造主体。
- Trace、审计和策略决策必须使用同一个 `actor_id` 语义，需要追溯人类账号时同时记录 `user_id`。

## 11. 工作空间隔离与授权

工作空间是默认数据隔离边界，授权采用默认拒绝：

- 所有工作空间业务表包含 `workspace_id`，全局平台配置必须显式标记为全局资源。
- Repository 接口必须要求可信 `workspace_id` 或作用域对象，禁止提供容易漏过滤的全局 `get_by_id(id)`。
- 读取、更新、删除、聚合统计、全文检索、向量检索和对象存储路径都必须执行工作空间约束。
- 更新和删除应把 `workspace_id` 写进同一 SQL 条件，不能先查后仅按资源 ID 修改。
- 菜单可见性和前端按钮状态不构成授权；每个后端用例仍校验 `permission_code`。
- 统一策略中心是 RBAC、资源级 ABAC 和字段级 ABAC 的唯一决策来源，业务模块不得复制简化规则。
- `resource_scope` 由实际读取数据的责任模块转换为可执行过滤条件；`field_mask` 在响应和日志生成前应用。
- 策略中心超时、不可用、版本不兼容或返回无法验证时默认拒绝。
- 涉及发布、审批、删除、敏感字段和工具执行的决策不得使用过期缓存。
- 资源不存在和无权限的外部响应需避免泄漏跨空间资源是否存在，具体错误映射按错误码契约执行。

任何新增工作空间资源必须同时交付正向授权、跨空间越权、字段泄漏和直接 ID 猜测测试。

## 12. Application 用例与事务

Application 用例是业务事务和授权编排入口。推荐顺序如下：

1. 校验 RequestContext 和 Command/Query 的结构及基础约束。
2. 授权需要资源属性时，只按可信 `workspace_id` 读取最小属性，且不能向调用方暴露未授权数据。
3. 调用统一策略接口完成授权。
4. 在 Unit of Work 中读取或重新确认当前状态并修改业务聚合。
5. 写入审计事实和需要可靠发布的 Outbox 事件。
6. 一次提交业务数据、审计事实与 Outbox。
7. 返回领域结果，由 Router 映射为 HTTP Response。

必须遵守：

- 事务由 Application 用例控制，Router、Repository 和领域实体不得自行 `commit`。
- 一个用例默认使用一个短事务；禁止在数据库事务内等待模型生成、OCR、大文件传输或不受控外部网络。
- 业务数据与对应 `OutboxEvent` 必须在同一数据库事务提交。
- 外部副作用采用“先记录意图/状态并提交，再由 Worker 执行”的方式，不能假装数据库和外部系统具有分布式事务。
- 失败必须整体回滚；捕获异常后不得在未知事务状态下继续复用 Session。
- 高风险写操作必须支持幂等键，幂等结果与业务提交保持一致。
- 并发更新使用版本号、状态条件或数据库约束防止丢失更新；不得只靠进程内锁。
- 授权依赖的资源属性可能并发变化时，高风险写入必须在事务中重新校验版本或授权条件，避免授权检查与提交之间的状态漂移。

## 13. SQLAlchemy 与 Repository

- 使用 SQLAlchemy 2 风格的显式查询和类型化映射，不新增旧式隐式 Query 写法。
- Session 生命周期由请求或任务的 Unit of Work 管理，禁止全局共享 Session。
- Repository 按业务聚合提供语义化方法，不暴露任意表名、任意过滤器或通用 `save(anything)`。
- Repository 不执行授权决策，但必须执行调用方传入的可信工作空间/资源范围。
- 禁止跨模块直接查询或写入其他模块私有表；需要的信息通过公开查询接口、只读投影或事件获得。
- 避免 N+1 查询；加载策略必须由用例需要明确选择，不能依赖序列化时触发隐式查询。
- 唯一性、外键、非空、检查约束和必要的工作空间复合索引必须在数据库落实，不能只依赖应用校验。
- 批量操作必须说明最大批次、事务范围、失败策略和资源消耗。
- 原生 SQL 只在 ORM 无法清晰或高效表达时使用，必须参数化并覆盖工作空间隔离测试。

不建立全局 `BaseRepository` 或万能过滤 DSL。重复代码只有在形成稳定语义和真实复用后才抽取。

## 14. Migration 与数据演进

- Alembic 是共享数据库唯一 Migration 工具；未来引入 Go 后仍不得同时使用第二套工具修改同一 Schema。
- Migration 文件一经进入共享历史不得修改；修正使用新的向前 Migration。
- Schema 变更采用 Expand/Contract：先兼容性新增，再迁移数据和调用方，最后在独立版本删除旧结构。
- 生产和真实数据环境禁止应用启动时自动执行 Migration。
- 高风险 Migration 必须检查锁表时间、磁盘空间、回填批次、失败恢复和旧版本兼容性。
- 数据回填应可重复执行、可观测且有断点，不能把长时间不可控循环塞入单次事务。
- 升级依靠执行前备份和恢复演练，不依赖不可靠的 Down Migration 作为唯一回滚方式。
- 每个数据库节点至少验证从空库建库和从上一受支持版本升级。

## 15. 契约与错误处理

接口事实来源按以下顺序确定：

1. `contracts/openapi/`、`contracts/sse/`、`contracts/events/`、`contracts/policy/` 和 `contracts/errors/`。
2. FastAPI 生成并通过一致性测试的 OpenAPI。
3. 已批准的架构决策和业务规格。

- 同一主版本只允许兼容性新增；删除、改名、收紧枚举或改变语义必须发布新主版本。
- 错误响应只暴露稳定错误码、可安全展示的信息、Trace ID 和明确可恢复信息。
- Python 异常类、数据库错误、供应商原始错误和堆栈不得直接进入外部响应。
- Domain/Application 使用少量稳定的领域错误；接入层集中映射 HTTP 状态与错误码。
- 未知异常统一记录脱敏上下文并返回内部错误码，禁止吞掉异常或返回伪成功。
- 供应商错误必须分类为超时、限流、认证、能力不支持、内容策略和内部失败，不能全部映射为同一字符串。
- 日志、指标和审计使用错误码聚合，不依赖易变化的异常文本。

## 16. Worker、Outbox 与幂等

- Worker 消息只携带稳定 ID、版本、幂等键和必要上下文，不携带 ORM 对象、明文凭证或大段二进制内容。
- 任务名称与载荷必须版本化，不使用 Python 模块路径作为长期协议。
- PostgreSQL 保存任务事实状态、进度、尝试次数和最终结果；Valkey 只负责队列、唤醒、锁或缓存。
- 任务按至少一次投递设计，处理器在发生重复、延迟和乱序时必须保持业务结果正确。
- 消费者以 `event_id` 或明确业务幂等键记录处理结果；不能只依赖队列声称的唯一投递。
- 同一聚合要求顺序时使用 `aggregate_id + aggregate_version` 检测缺失、重复和乱序。
- 重试只用于可安全重放的错误，采用有限次数和退避；验证错误、权限拒绝和不支持能力不得盲目重试。
- 每个任务必须定义超时、取消、最大重试、失败原因、死信或人工恢复路径。
- 外部调用执行前后保存可审计状态；不确定是否已产生副作用时不能直接重新执行。
- 任务入口保持轻量，业务逻辑进入可独立测试的 Application/Domain 模块。

## 17. SSE 与流式恢复

- SSE 连接只负责事件传输，`MessageEvent` 和最终 `Message` 才是恢复事实来源。
- 每个事件包含稳定 `event_id`、会话/运行 ID、严格递增 `sequence_no`、事件类型、时间、Trace 和可校验载荷。
- 事件持久化成功后才能视为可恢复；不得只保存在连接实例内存。
- `Last-Event-ID` 回放必须处理不存在、重复、过期、超过回放上限和最终快照恢复。
- 断线重连不能创建新的 `Run` 或重复触发模型生成。
- 同一会话的并发生成执行明确锁或状态约束，跨进程正确性不能依赖进程内变量。
- 心跳、业务结束、用户取消、服务错误和连接断开使用不同事件或状态表达。
- 回放上限、24 小时保留和清理必须可配置、可测试且不破坏最终消息事实。
- 流式 Adapter 负责供应商事件归一化，业务层不得依赖供应商私有 Chunk 类型。

## 18. 外部系统与模型网关

- 业务模块、Router 和普通 Worker 不得直接调用模型供应商；所有模型访问经过模型网关。
- 外部系统通过窄接口和 Adapter 隔离协议差异，超时、重试、熔断、限流和错误映射集中管理。
- HTTP Client 必须设置连接、读取和总超时；禁止无期限等待。
- 调用方传递取消信号或截止时间时，Adapter 应在底层能力允许时传播。
- 重试必须考虑方法幂等性、请求体可重放性、供应商限流提示和成本副作用。
- 自定义模型 `base_url` 执行 HTTPS、域名允许列表、DNS 重绑定、内网地址和重定向检查。
- 模型 API Key 只在服务端最小范围解密，不进入浏览器、Prompt、模型上下文、普通日志和导出文件。
- 供应商兼容性必须分别探测普通响应、SSE、结构化输出、工具、Usage、错误码、限流和请求 ID，不能只凭“兼容 OpenAI”声明判定。
- 测试默认使用 Mock/Fake Adapter；真实供应商测试必须显式标记并只发送被数据政策允许的样本。

## 19. 配置、密钥与安全

- 配置统一通过类型化 Settings 读取，业务模块不得直接读取环境变量。
- 配置键使用 `AI_PLATFORM_` 前缀；默认值只能用于本地安全配置，生产必填项不得悄悄回退到弱默认值。
- 配置加载时校验 URL、范围、容量和相互依赖关系，错误应在启动或能力启用前暴露。
- 平台主密钥和供应商密钥不得进入 Git、镜像层、普通备份、日志或错误详情。
- 密钥保存后不可回显，轮换必须保留版本、审计和受控回退能力。
- 用户输入的文件名、URL、模板、查询和富文本视为不可信数据，执行路径穿越、SSRF、注入和内容大小防护。
- 日志脱敏至少覆盖 Authorization、Cookie、Session、API Key、密码、令牌和受字段级 ABAC 保护的值。
- 合成测试数据与真实数据明确隔离；本地测试禁止使用真实个人、企业或供应商敏感资料。

## 20. 可观测性与审计

- HTTP、任务、Outbox、SSE、检索和模型调用传播 W3C `traceparent`，不自行发明不兼容 Trace 格式。
- 结构化日志至少包含时间、级别、服务、环境、事件名、Trace、请求/任务 ID 和稳定错误码。
- 在数据政策允许时记录 `actor_id`、`workspace_id`、资源类型和资源 ID；禁止记录敏感字段正文。
- 日志事件名稳定且可聚合，不把自然语言消息作为唯一机器查询字段。
- 指标使用有界标签，禁止把用户 ID、文档 ID、Trace ID 或原始错误文本作为高基数标签。
- 审计日志与运行日志职责不同：权限决策、发布、审批、密钥变更和高风险操作必须形成不可随普通日志清理而丢失的审计事实。
- 关键链路记录延迟、结果、重试、用量与成本，但不得为了观测复制完整用户内容。
- 捕获异常时保留原始异常链；外部响应保持稳定错误码，内部日志保留可定位信息。

## 21. 同步、异步与性能

- 不规定所有函数都使用 `async`。一个 I/O 模块必须选择一致、可验证的执行模型，不能在异步调用链中隐藏阻塞 I/O。
- FastAPI 同步端点可用于短时同步操作；外部网络、数据库和流式连接采用异步实现时，整条相关调用链保持异步。
- 阻塞型解析、OCR、Embedding、大文件处理和长时间模型任务进入独立 Worker。
- 禁止在事件循环中直接使用阻塞 SDK；没有异步 Adapter 时使用受控线程池并设置并发上限和超时。
- 数据库连接池、HTTP 连接池、Worker 并发和 SSE 连接数必须配置化并具有本地安全默认值。
- 先通过指标、查询计划或性能测试定位问题，再引入缓存、批处理和并发；不得用缓存掩盖错误的数据边界。
- 缓存 Key 必须包含影响结果的 `workspace_id`、策略版本和资源版本；权限变更时可精确失效。
- 大列表、导出、解析和回放必须定义上限、分页/分批策略和背压，不允许无界加载到内存。

## 22. 测试规范

测试按风险和接口设计，不以单一覆盖率数字替代业务验收：

| 测试类型 | 主要责任 |
| --- | --- |
| 单元测试 | 领域规则、状态转换、纯函数和错误分支 |
| Application 测试 | 授权、事务编排、幂等和依赖交互 |
| 集成测试 | PostgreSQL、Valkey、对象存储、策略过滤和 Migration |
| 契约测试 | OpenAPI、SSE、事件、错误码和 Golden Fixtures |
| 安全测试 | 跨工作空间、字段泄漏、直接 ID、SSRF 和凭证脱敏 |
| 恢复测试 | Outbox 重投、Worker 重试、SSE 回放和备份升级 |

必须遵守：

- 测试通过公开接口或稳定模块接口验证行为，避免绑定内部私有步骤。
- 时间、UUID、随机数、外部网络和任务调度通过注入的依赖或 Fake 控制。
- Fake/Mock 必须保留真实接口的重要约束，不能让不可能在生产出现的调用通过。
- 权限、字段级 ABAC、事务、Outbox、Worker 幂等、SSE 和 Migration 必须包含真实基础设施集成测试。
- 每个工作空间资源至少覆盖同空间允许、跨空间拒绝、缺少上下文拒绝和字段掩码。
- 错误测试断言稳定错误码和状态，不依赖完整自然语言文本或 Python 异常类。
- 测试 Fixture 只使用明确标记的合成数据。

每个 Python 后端节点至少执行：

```bash
uv run --locked ruff format --check .
uv run --locked ruff check .
uv run --locked mypy .
uv run --locked pytest
```

节点最终验收统一执行 `./scripts/verify`；上述命令用于 Python 开发过程中的快速反馈。正式领域分层目录创建后，Python 架构检查会自动验证 Domain、Application、API 与 Infrastructure 的依赖方向。

影响契约、数据库、权限、Worker 或 SSE 时，必须追加对应的契约、集成、安全或恢复测试，不能仅执行现有快速测试后宣告完成。

## 23. 注释与文档

### 23.1 基本原则

- 新增和修改的代码注释统一使用中文，优先说明业务意图、设计原因、数据责任和维护风险，不复述代码表面行为。
- 注释必须与实现、契约、状态机和当前架构决策一致；行为变化时同步更新注释。
- 先用清晰命名、深模块接口和合理拆分表达简单逻辑，不用注释掩盖职责过重或依赖方向错误。
- 不采用“每 N 行必须有注释”的机械指标，也不为简单赋值、字段声明和显然的转换增加低价值注释；注释密度由分层职责、公开接口数量、事务和业务流程复杂度决定。

### 23.2 模块与公共接口说明

除生成文件外，`apps/api/src`、`apps/worker/src` 和 `packages/backend/src` 下所有手写 Python 文件必须把模块级 docstring 作为第一条语句，`from __future__` 位于其后。简单包入口至少说明公开领域；领域模块、Application 用例、Router、Repository/Unit of Work、外部 Adapter、Worker 消费者、SSE 存储和跨模块基础设施还必须说明负责什么、不负责什么、依赖边界、数据写入权以及事务、权限或外部副作用约束。

所有公开的顶层类和函数必须有 docstring。Application Service、Worker Task/Consumer、SSE 服务、模型 Gateway、解析器和密钥 Cipher 的公开方法必须进一步说明调用前置条件、返回事实、稳定错误模式、幂等语义或事务要求。Domain Protocol、Repository 和 Unit of Work 在类型级 docstring 统一说明方法集合的权限、事务与一致性契约；只有单个方法存在额外非直观约束时才单独说明。具体 Adapter 实现复用其 Protocol 契约，由类级 docstring 补充 Session、锁、网络和外部副作用差异，避免每个实现方法重复相同说明。简单私有函数、Pydantic 直映射字段和显然的赋值不强制逐项说明。

公开 Pydantic Schema 的字段说明以 OpenAPI 契约源为准；只为默认值、省略行为、安全投影或兼容语义不直观的字段补充 `Field(description=...)`，禁止复制一份可能漂移的接口文档。Domain dataclass、Protocol 参数和回调中具有状态、单位、时区、敏感级别或所有权语义的字段必须在类或方法 docstring 中说明。

```python
class RegistrationUnitOfWork(Protocol):
    """注册事务边界。

    账号、个人空间、所有者关系、审计和 Outbox 必须在同一事务中提交；
    该接口不负责密码哈希、HTTP 响应映射或外部通知。
    """
```

自动生成的 OpenAPI 类型、第三方代码和协议固定文本不手工改写注释，应修改生成源或保留原始格式。Alembic 固定元数据保持生成格式，但手写的约束建立顺序、历史数据回填和不可逆降级步骤必须补充中文说明。

### 23.3 必须解释的后端业务边界

函数包含三个及以上业务步骤、多个有顺序依赖的外部调用，或以下逻辑时，必须在职责最近的位置添加中文块注释。线性用例使用 `# 1. ...`、`# 2. ...` 编号；非线性规则说明“为什么这样做”：

- `workspace_id` 隔离、默认拒绝、资源不存在与无权限的错误映射；
- 字段级 ABAC、敏感字段投影和禁止数据进入日志/检索/模型上下文的出口；
- Application 用例、Unit of Work、Repository 的事务边界和提交责任；
- 状态机、版本指针、不可变快照和并发更新条件；
- Outbox、事件发布、重复消费、幂等键、租约、有限重试和死信策略；
- Worker 不在 API 进程执行大文件、OCR、模型调用或不可控外部网络的原因；
- SSE 事件序号、`Last-Event-ID`、回放保留期、取消和恢复事实；
- 模型/对象存储/HTTP Adapter 的超时、重试、脱敏、SSRF 和失败关闭策略；
- Migration、兼容窗口、回滚和历史数据回填的非直观约束。

行内注释只用于保存点、锁、竞态、临界值、特殊兼容、安全限制或防止未来误删的代码。例如：

```python
# 保存点只回滚幂等冲突，不能把调用方外层事务置为 failed。
with session.begin_nested():
    ...
```

一个步骤注释应覆盖相邻的完整事务或业务逻辑块，通常为 3～10 行；不得为每个赋值、普通查询和返回语句添加逐行注释。分层补充要求如下：

- Domain 说明不变量、合法状态转换、拒绝原因和不可变快照边界。
- Application 说明可信上下文来源、授权顺序、事务步骤以及审计/Outbox 的同事务要求。
- Repository 说明工作空间过滤、锁、唯一约束、乐观并发和查询取舍。
- API 说明协议映射、上下文注入、稳定错误码和字段投影边界。
- Worker 说明幂等键、租约、有限重试、死信和提交时机。
- 模型与对象存储 Adapter 说明脱敏、SSRF、超时、重试和失败关闭策略。
- SSE 说明序号、保留期、回放上限、取消和最终快照恢复关系。

长函数内部注释按有效代码行执行以下分级规则：

- 少于 30 行不因长度强制分段，但权限、事务、锁、状态机、幂等、外部副作用和敏感数据处理仍按风险要求说明。
- 30～59 行进入检查范围；检测到两个以上控制流、事务或外部调用阶段时，必须使用连续编号的中文注释标出重要阶段。
- 60～99 行必须使用连续编号的中文注释划分主要流程，通常不少于三个阶段，并同时评估是否可以提取领域校验器、Application 私有步骤或 Repository 深模块。
- 100 行及以上默认拆分；确因不可拆事务、状态机完整性、批量映射或兼容算法保留时，必须在函数内使用“长函数保留原因：”说明取舍，并继续满足阶段注释要求。

有效代码行不计算函数签名、docstring、空行、注释、纯类型声明以及仅含括号或分隔符的排版行。长度只是发现维护风险的信号，不能通过拆成多个无语义的转发函数或添加“处理数据”“执行操作”等模板注释规避门禁。

### 23.4 文件类型最低要求

| 文件类型 | 最低注释要求 |
| --- | --- |
| 所有手写 Python 模块 | 第一条语句为模块 docstring；公开顶层类和函数具有 docstring |
| 模块入口 | 公开领域、依赖方向、数据写入权和不负责的内容 |
| Router | 公开端点 docstring；协议映射、身份/工作空间上下文和错误转换边界 |
| Application 用例 | 公开服务/方法 docstring；授权顺序、事务范围、幂等和外部副作用分离原因 |
| Domain 模型/Protocol | 公开类型 docstring；状态规则、前置条件、异常和可替换边界 |
| Repository/UoW | 公开 Adapter docstring；聚合写入权、Session 生命周期、锁/版本和提交责任 |
| Worker/Consumer | 事件版本、幂等键、重试/死信和租约恢复策略 |
| SSE 服务 | 事件事实来源、序号、回放、过期、取消和恢复行为 |
| 外部 Adapter | 数据脱敏、超时、重试、能力差异和失败关闭策略 |
| Migration/回填脚本 | 可重复执行、批次、断点、回滚和数据影响 |
| 测试文件 | 被验证的业务边界、合成数据约束和故障场景 |

### 23.5 注释与契约同步

HTTP、SSE、事件、错误码、数据库字段、状态机或数据写入权发生变化时，必须同步 `contracts/`、设计文档、数据责任表和验证报告。注释不能成为唯一的契约来源，也不能用过期注释掩盖实现与契约不一致。

### 23.6 注释质量门禁

`scripts/check_python_comments.py` 使用 Python AST 检查全部当前手写源码，至少覆盖：模块 docstring、公开顶层类和函数 docstring、指定分层公开方法 docstring、长函数有效代码行、连续编号阶段注释、100 行函数保留原因、TODO/FIXME/HACK 格式以及生成文件排除边界。检查接入 `./scripts/verify`，任何当前文件违规都阻断节点验收，不保留历史告警白名单。

自动门禁只判断可确定的结构事实，不能用 docstring 数量替代语义质量。复杂事务是否已解释步骤、注释是否只是复述代码，继续由实现者写后清单和代码审查负责；不得用类名或函数名机械拼接一句话绕过检查。

TODO/FIXME/HACK 必须包含责任角色、日期和退出条件，例如：`TODO(@backend 2026-09): 策略版本事件上线后删除短轮询兼容逻辑`。

具体注释要求同时执行仓库根目录 `AGENTS.md` 和本机全局注释规范；发生冲突时采用更严格且不会产生低价值注释的规则。

## 24. Git 与质量门禁

- 提交执行 [`delivery-and-git.md`](./delivery-and-git.md)，一个可验收节点对应一个独立提交。
- 提交信息使用 `<type>(<节点 ID>): <中文摘要>`，后端常用类型为 `feat`、`fix`、`refactor`、`test`、`docs`、`chore` 和 `perf`。
- Ruff 格式、Lint、mypy、pytest、契约、安全或 Migration 检查失败时，不得标记节点完成。
- 自动修复只处理本次范围文件；大面积无关格式变化必须移出当前业务提交。
- 依赖升级必须提交锁文件，说明兼容影响，并通过对应测试和安全检查。
- 破坏性契约或数据库修改必须具有迁移、兼容窗口和回滚方案，不能作为内部重构的附带变化。

## 25. 未来 Go 演进约束

当前规范以 Python 实现为主，但以下规则必须保持语言无关：

- 跨模块和跨进程只传递 OpenAPI、JSON Schema、稳定错误码与版本化事件，不传递 ORM、异常类、Pickle、模块路径或框架上下文。
- Python 与未来 Go 使用同一套 Golden Fixtures、策略越权、Trace、幂等、乱序和恢复测试。
- 一个业务聚合任一时刻只有一个正式写入实现，不采用长期双写。
- Go 接入层不能复制策略规则，也不能自行拼接由 Python 责任模块执行的数据/字段授权条件。
- 数据写入权迁移必须整体切换状态机、幂等、事务和 Migration 责任，并经过影子验证与回滚演练。
- 只有达到架构定义的量化迁移条件后才选择 Go 框架和依赖；当前不创建空 Go 工程。

未来建立 Go 代码规范时，应复用本规范的模块职责、契约、安全和数据所有权原则，并只补充 Go 特有的类型、并发、错误和工具链规则。

## 26. 禁止的反模式

- 在 Router 中编写业务规则、SQL、权限判断或事务提交。
- 建立万能 `BaseService`、`BaseRepository`、CRUD 生成器或任意过滤 DSL 逃避领域设计。
- 每个简单功能机械创建四层、接口和 Adapter，却没有变化点和额外行为。
- 业务模块绕过统一策略中心、模型网关或数据责任模块。
- 使用菜单可见性、前端传入角色或资源 ID 存在性代替后端授权。
- 将 ORM 对象放入 HTTP 响应、Celery 参数、缓存、SSE 或集成事件。
- 在数据库事务中执行不可控模型调用、OCR、大文件上传或远程请求。
- 将 Valkey、进程内存或任务队列状态作为最终业务事实。
- 捕获 `Exception` 后静默忽略、返回成功或无限重试。
- 用长期双写、第二套 Migration 或复制权限规则为未来 Go 做准备。
- 为追求覆盖率编写只断言实现细节、没有业务风险价值的测试。

## 27. 阶段 1 落地顺序

规范生效后，新代码立即遵守不依赖新增工具的规则。工程能力按以下顺序建设：

1. 在阶段 1A 建立 `app/` 与首批真实业务模块目录、可信 `RequestContext`、统一错误映射和依赖装配。
2. 固定 SQLAlchemy Session、Unit of Work、Repository、Alembic 和测试数据库模式。
3. 随工作空间与组织模块验证强制 `workspace_id`、数据写入权和越权测试。
4. 随策略与菜单模块验证 `permission_code`、`resource_scope`、`field_mask` 和默认拒绝。
5. 随知识生产和模型网关建设 Worker 幂等、有限重试、外部 Adapter、配置与密钥规范。
6. 随 RAG/SSE 建设事件持久化、顺序、回放、取消、Trace 和用量记录。
7. 将契约、PostgreSQL 集成、Migration、安全与恢复检查接入自动质量门禁。
8. 将注释质量检查接入每个后端节点的验收，新增和实际修改文件阻断，历史文件先告警。

任何规则调整必须同步本文档、相关配置、契约和验证报告。实际代码与文档冲突时，不能只修改说明来掩盖实现偏差；应明确判断是修复实现还是通过独立架构决策修订规范。
