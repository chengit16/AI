# 架构决策管理规范

## 1. 使用目的

ADR 用于记录会长期约束模块接口、数据、协议、安全、部署或运维方式的关键决策。ADR 解释“为什么选择”，代码规范说明“之后怎样实现”，二者不能相互替代。

模板见 [`ADR-template.md`](../decisions/ADR-template.md)。正式文件使用 `docs/decisions/ADR-NNN-kebab-case.md`，编号只增不改。

## 2. 必须创建 ADR 的情况

- 引入、替换或移除核心框架、数据库、队列、模型协议、身份认证或部署方式。
- 改变模块接口、依赖方向、业务聚合写入权或服务拆分方式。
- 改变 OpenAPI、SSE、事件、错误码的主版本或兼容策略。
- 改变工作空间隔离、RBAC/ABAC、密钥、审计和数据生命周期规则。
- 引入长期缓存、双写、影子流量、Feature Flag 平台或重大性能优化。
- 选择会影响备份恢复、Migration、SSE 保留、Prompt/模型路由版本的实现。
- 通过量化条件决定将某个 Python 模块迁移为 Go。

普通 Bug 修复、依照已有规范实现新页面/用例、可逆的小范围重构和单纯版本补丁升级通常不需要 ADR。

## 3. 决策流程

1. 在实施前创建状态为“拟议”的 ADR，写明背景、驱动因素和至少两个可行方案；确实只有一个方案时说明原因。
2. 使用契约、安全、恢复、性能或原型证据评估，不只比较代码量。
3. 决策确认后改为“已接受”，同步相关架构、规范、计划和检查器。
4. 后续改变决策时创建新 ADR，将旧 ADR 标记为“已取代”并互相链接，不重写历史原因。
5. ADR 随实际实施节点提交；纯决策节点也必须执行文档与 Git 门禁。

## 4. 评审要求

- 决策必须指出模块接口、数据写入权、调用方和测试面的变化。
- 安全或权限相关决策必须采用默认拒绝并列出越权反例。
- 破坏性契约和 Migration 必须具有兼容窗口与恢复路径。
- 性能优化必须说明测量方法和触发阈值。
- 后置事项必须包含进入条件，不能用“以后优化”代替责任与退出标准。
