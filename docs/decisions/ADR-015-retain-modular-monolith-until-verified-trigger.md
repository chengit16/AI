# ADR-015：在可验证触发条件成立前保留模块化单体

## 状态

已接受

## 日期

2026-08-18

## 背景

设计文档 17.8 节要求服务拆分由独立扩缩容、团队所有权、故障隔离、合规部署或可测量瓶颈驱动；Go 演进还必须至少满足一项连接、资源、延迟、Runtime 隔离或团队运维条件，并形成可归因基准报告。17.9 节进一步固定影子流量、共享契约、单一写入权和回切 Python 的迁移顺序。

当前平台已经完成模块化单体、独立 Worker、控制面与运行面边界、L3 隔离迁移和 L4 独立实例交付，但容量认证仍为 `not_run`，生产负载画像、团队所有权分工和 Go 运维能力均为 `not_configured`。阶段 2 的可靠性演练和本地统一门禁只能证明当前实现的功能与恢复机制，不能替代 5,000 持续 SSE 连接、目标机器 CPU/内存/P95 或生产交付瓶颈基准。

## 决策驱动因素

- 未经基准报告验证的性能猜测不能创建第二套生产运行时。
- `not_run` 和 `not_configured` 只能阻止迁移授权，不能被解释为性能通过或条件已触发。
- Python 继续保持业务聚合和当前运行事实的唯一写入权，禁止为影子验证建立长期双写。
- L3/L4 数据与实例隔离不自动等于某个应用模块需要拆成独立服务。
- 未来若触发，必须复用现有 OpenAPI、SSE、事件、错误码、策略、Trace 和安全测试。

## 触发审计

| 类别 | 17.8 节条件 | 当前状态 | 当前事实 |
| --- | --- | --- | --- |
| 服务拆分 | 独立扩缩容且现实现经优化仍不达标 | `not_run` | 容量认证未执行，没有可归因压测报告 |
| 服务拆分 | 团队所有权和发布节奏长期不同 | `not_configured` | 未配置长期团队所有权记录 |
| 服务拆分 | 明确的故障隔离要求 | `not_configured` | 未配置新的目标故障域；现有本地演练不外推生产要求 |
| 服务拆分 | 数据合规要求独立部署 | `not_configured` | 客户环境与真实合规输入未配置；L4 当前仅完成本地机制 |
| 服务拆分 | 单体存在可测量性能或交付瓶颈 | `not_run` | 没有生产负载画像或归因基准 |
| Go 演进 | SSE 持续超过 5,000 或 Python 不满足稳定性/内存目标 | `not_run` | 条件容量认证未执行 |
| Go 演进 | 网关或模型流式代理 CPU、内存或 P95 成为主要瓶颈 | `not_run` | 未执行可归因资源与延迟基准 |
| Go 演进 | Agent Runtime 需要独立扩缩容或故障隔离 | `not_configured` | 未配置目标 Runtime 容量或故障域要求 |
| Go 演进 | 具备明确负责人、运维能力和回滚窗口 | `not_configured` | 未配置 Go 所有权和生产运维输入 |

九项条件均没有 `triggered` 事实，当前基准报告状态为 `not_run`。这表示“没有迁移授权”，不表示生产容量、性能或组织条件已经达标。

## 备选方案

### 方案 A：立即创建 Go 接入层和 Runtime 骨架

可以提前探索工具链，但会产生第二套依赖、镜像、权限与运维表面，在没有目标负载和负责人时无法证明收益，也容易诱发契约漂移，因此拒绝。

### 方案 B：先按模块拆成多个 Python 微服务

可以获得进程级隔离，但当前没有独立扩缩容、发布节奏或故障域证据。拆分会引入网络失败、分布式事务和部署复杂度，且不能自动解决未知性能问题，因此拒绝。

### 方案 C：保留模块化单体与独立 Worker，建立版本化触发审计

保持当前写入权和部署形态，用 `p5-11-v1` 契约逐项保存真实状态。只有出现已验证触发项时才重新立项，采用此方案。

## 决策

- 当前决策为 `retain_modular_monolith`，原因码为 `no_verified_trigger`。
- 不创建 `services/edge-gateway/`、`services/agent-runtime-go/`、Go Module、第二套 Migration 或长期双写路径。
- 现有 Python 模块化单体、五类独立 Worker、统一策略中心和单一 Alembic 历史保持不变。
- 本 ADR 不把容量、生产性能、真实团队条件或 Go 运维能力标记为通过；这些状态继续为 `not_run/not_configured`。
- 任一未来触发声明必须引用可复核证据。性能和连接类声明还必须与通过的容量或生产负载基准一致，否则失败关闭。

## 影响

### 正面影响

- 避免在收益不可测量时承担第二种后端语言和分布式部署成本。
- 保持当前权限、工作空间隔离、事务和数据写入权边界可验证。
- 未来演进仍有稳定触发项、证据格式和迁移门禁，不依赖口头判断。

### 负面影响与残余风险

- 当前没有形成生产容量上限，无法判断 Python 接入层在目标机器上的最大稳定 SSE 连接数。
- 缺少生产负载画像时，CPU、内存和 P95 的潜在瓶颈仍未知。
- 若团队结构或客户合规要求变化，必须重新执行审计，当前结论不能永久外推。

## 验证指标

- `p5-11-v1` 完整列出 5 项服务拆分条件和 4 项 Go 条件，不允许缺项、重复或乱序。
- `not_run/not_configured` 的外部状态不能被改写为 `triggered`。
- 启动 Go 必须同时存在已验证拆分条件、已验证 Go 条件和 `passed` 基准报告。
- 当前仓库不存在两个预留 Go 服务目录，运行事实仍由 Python 单写。
- 低敏验收证据只保存状态和计数，不复制负载、团队或客户合规正文。

## 迁移与回滚

未来触发后必须先形成新的 ADR，再按以下顺序执行：

1. 复用版本化共享契约，以反向代理和只读影子流量比较结果。
2. 通过契约、安全、工作空间隔离、Trace 和故障演练后，按功能开关逐步放量。
3. 涉及数据时停止 Python 旧写入、切换路由、启用新写入并验证；任何时刻只有一个责任实现写入。
4. 回滚窗口内保留按路由切回 Python 的能力；失败时先停止新写入，再恢复原路由和原写入权。
5. 回滚窗口结束后才能清理旧实现，不建立长期双写。

## 后续事项

- 获得目标机器、生产负载画像和容量预算后，独立执行容量认证并更新触发审计。
- 出现明确团队分工、故障域或客户合规独立部署要求时，附可复核责任记录重新审计。
- 在任何 Go 实现开始前确认负责人、监控、值班、发布和回滚窗口已经配置。
