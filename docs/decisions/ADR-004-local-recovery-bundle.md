# ADR-004：本地加密恢复包与主密钥轮换

## 状态

`已接受`

## 日期

2026-08-15

## 背景

阶段 1 本地 MVP 已同时使用 PostgreSQL、MinIO、Valkey 和文件型密钥。PostgreSQL 保存业务、授权、审计、Outbox、SSE 与任务事实；MinIO 保存上传原件和解析/索引产物；Valkey 只保存可失效、可重建的 Session、缓存、Broker 和唤醒状态。模型供应商 Key 采用 AES-256-GCM 信封加密，数据库中的凭据密文只有配合原平台主密钥和对应版本才能恢复。

如果只复制数据库，会得到指向不存在对象的事实；如果只复制数据目录，会把数据库和 MinIO 置于不同时间点；如果普通备份不包含平台主密钥，供应商凭据即使完整恢复也无法使用。项目还需要本地导出、导入和升级/回滚演练，但不应维护第二套容易漂移的数据格式。

## 决策驱动因素

- 恢复包必须同时覆盖 PostgreSQL 事实、MinIO 对象和恢复供应商凭据所需的文件型密钥。
- 备份前后必须验证数据库对象引用与 MinIO 实体一致，不能把缺失对象静默带入备份。
- 包内可能包含密码 Hash、业务正文、审计事实和主密钥，必须在落盘前整体加密并认证。
- 恢复包加密密钥不能与包内平台主密钥相同，也不能被放入恢复包或 Git。
- 本地导出/导入与备份/恢复应共享一种版本化格式、Manifest 和校验流程。
- Migration 必须在恢复到干净数据库后实际完成降级与再升级，空库结构测试不能替代数据恢复演练。

## 备选方案

### 方案 A：直接复制 `.ai-platform` 整个目录

实现最少，但 PostgreSQL 和运行中的 MinIO 文件并非一致快照，复制时还会混入 Valkey、日志、临时运行状态和与当前版本绑定的存储内部细节。未加密目录也会直接暴露业务数据与密钥，不满足安全和可验证恢复要求。

### 方案 B：只保存 PostgreSQL Custom Dump

逻辑数据库恢复和跨 macOS/Linux 可移植性较好，但上传原件、解析产物、索引产物及主密钥均缺失，数据库引用不能闭环，供应商凭据无法解密。

### 方案 C：版本化加密恢复包

在短暂停写窗口中使用 PG16 Custom Dump 保存 PostgreSQL，停止 MinIO 后保存固定版本的对象数据快照，并加入平台主密钥、任务签名密钥及主密钥版本。包内使用 Manifest 记录 Schema Revision、明确排除项、逐文件大小和 SHA-256；外层使用独立 32 字节恢复密钥执行流式 AES-256-GCM 加密与认证。该方案需要维护运维编排，但能提供完整、可验证且可迁移的本地恢复边界。

## 决策

采用方案 C，并固定以下规则：

1. 恢复包格式为 `ai-platform-recovery` V1，文件后缀为 `.aiprb`。`backup/restore` 与 `export/import` 共用同一格式，不创建第二套数据语义。
2. 创建恢复包前先检查 PostgreSQL 中上传原件、解析产物和索引产物的对象键都能在 MinIO 读取；任一引用缺失时失败关闭。
3. 先停止 API、Worker 和 MinIO 写入，再在同一停写窗口生成 PostgreSQL Custom Dump 和 MinIO 物理对象快照。对象物理快照只保证恢复到当前固定 MinIO 版本；未来改用外部 S3 时必须新增逻辑对象导出 Adapter 和新格式版本。
4. 包内必须包含 `database.dump`、`objects.tar`、`master.key`、`master.key.version` 和 `task-signing.key`。恢复包加密密钥保存为 `.ai-platform/secrets/backup-encryption.key`，权限为 `0600`，不进入包内、数据库、日志或 Git。
5. 恢复包使用流式 AES-256-GCM，固定头同时作为关联数据；错误密钥、密文或认证标签变化均失败。解包拒绝绝对路径、路径穿越、符号链接、设备文件、额外文件、缺失文件和校验和漂移，并只向空目录发布已经完整验证的内容。
6. 恢复属于替换本地事实的破坏性操作，必须使用 `--confirm-replace`，并在替换前自动创建独立的预恢复加密包。恢复期间服务停止；任何中途失败均不得自动暴露半恢复状态。
7. Valkey、日志和 `runtime` 明确不进入恢复包。导入后清空 Valkey，Session 失效，缓存重新计算，Broker/唤醒状态由 PostgreSQL Outbox 和任务事实恢复；审计记录仍随数据库恢复。
8. 主密钥轮换前自动备份。轮换只使用新主密钥重新包裹每条供应商凭据的数据密钥，供应商 Key 正文密文和数据 Nonce 保持不变；全部凭据在单一数据库事务中更新，主密钥版本单调递增。
9. 本地默认恢复目录为 `AIPlatformBackups/`，可通过 `AI_PLATFORM_BACKUP_ROOT` 覆盖；本地数据目录继续由 `AI_PLATFORM_ROOT` 管理。两者均不进入 Git。

## 影响

### 正面影响

- PostgreSQL、MinIO 和文件型密钥形成同一可校验恢复单元，避免数据库成功但对象或供应商凭据不可用。
- 导出/导入与备份/恢复共享格式、加密、Manifest、路径校验和对象一致性检查，减少长期漂移。
- Valkey 被明确定位为可重建状态，恢复不依赖 AOF 与数据库同时一致，也不会保留旧 Session。
- 主密钥可以在不触碰供应商 Key 正文的前提下轮换，并通过版本和数据库事务失败关闭。

### 负面影响与残余风险

- 本地一致备份需要短暂停止 API、Worker 和 MinIO，不是在线零停机备份；SaaS 或生产高可用方案需要独立设计。
- 当前对象快照依赖固定 MinIO 物理格式，只适用于本地同版本恢复；不能直接作为任意 S3 服务之间的迁移格式。
- 恢复加密密钥若与机器一起丢失，恢复包无法解密；若与恢复包存放在同一位置，机器外泄会同时暴露数据和平台主密钥。使用者必须把该密钥另行安全保管。
- 数据库事务与主密钥文件替换不能形成跨介质原子提交。轮换前恢复包是最终回退点；轮换失败时服务保持关闭，禁止用新旧密钥猜测性启动。

## 验证指标

- 恢复包密文中不能检索到数据库、对象或密钥明文；错误密钥、任一字节篡改和不安全 Tar 路径均被拒绝。
- Manifest 必需文件、额外文件、大小和 SHA-256 全部验证通过后，才能发布到空恢复目录。
- 真实 PostgreSQL Custom Dump 能恢复到干净数据库；恢复库从 `head` 降级一版再升级到 `head` 后，Revision、核心事实计数和对象引用一致。
- MinIO 对象存在时引用检查通过，删除任一引用对象后检查失败。
- 主密钥重包裹后供应商 Key 可由新密钥解密，旧密钥版本被拒绝，正文密文保持不变。
- `./scripts/verify` 和 `./platform doctor` 通过，恢复和轮换没有把真实凭据或密钥写入仓库与报告。

## 迁移与回滚

1. `P1G-03` 增加恢复包、对象引用检查、主密钥重包裹工具及 `./platform` 运维命令，不改变现有业务表结构。
2. `.env.example` 新增 `AI_PLATFORM_BACKUP_ROOT` 和 `MASTER_KEY_VERSION`；已有 `.env` 缺少配置时分别安全回退到 `./AIPlatformBackups` 和版本 1。
3. 首次备份时生成独立恢复加密密钥，已有合法密钥保持不变。该密钥不随普通启动生成，避免未使用恢复能力时扩大秘密数量。
4. 恢复前自动创建预恢复包；验证失败时不替换任何事实，替换中失败时保持服务停止并使用预恢复包回退。
5. 主密钥轮换前自动创建恢复包；数据库重包裹失败时事务回滚并保留旧密钥，文件替换后失败时使用轮换前恢复包回退。

## 后续事项

- 阶段 2 在此边界上增加定期备份策略、保留清理、恢复时间目标、故障注入和数据生命周期自动化。
- 外部 S3、SaaS、多节点 PostgreSQL 或在线备份需求出现时创建新 ADR，不直接扩展当前物理对象快照语义。
- 商业部署前将恢复加密密钥接入操作系统 Keychain、KMS 或受控离线介质，并建立双人恢复与轮换审计流程。
